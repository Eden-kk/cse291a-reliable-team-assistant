Formal evaluation v1 — design freeze 2026-10-24
Authoritative manifest: configs/formal-evaluation-v1.json. This is a preregistered design and spending ceiling, NOT an executable launch approval. No held-out observations or labels were opened. Model and launch annex remain blocked; any change is versioned before opening evaluation inputs.

1. Question and population
After a trusted source/artifact invalidation notification, does dependency-aware recovery reduce recomputation while preserving supported diagnosis and workflow validity? The notification identifies invalid material, never the diagnosis. Study one read-only Cloud-OpsBench application, not production incidents or general adversarial security. Irreversible external actions are excluded; local publication rejection is measured, not represented as undoing real actions.
Three independent incident IDs, first final_locked entry in each registry category: runtime/32, service/12, performance/5 (all boutique). Two stochastic repetitions each. The remaining five locked IDs are not substitutes. Same application/template overlap remains a generalization limitation. Six runs are not six independent incidents.

2. Fixed workflow and comparisons
Parallel-one topology: telemetry and configuration independently collect evidence; one coordinator diagnosis. Empty memory, no learning or scheduling changes. Maximum four tool attempts per collector, one diagnosis round. One model/configuration across all arms. Explicit temperature, seed support, tool schema, prompts, revision/alias, code and runtime hashes belong in a signed-off launch annex. Do not silently switch providers or models.
Save a clean collection snapshot and clean answer. Wrong-content arms fork from the saved collection snapshot BEFORE clean diagnosis, then run a separate contaminated diagnosis. Post-fault no-recovery, full restart and selective share this contaminated prefix and notification, with isolated state and equal per-call ceilings. No-recovery adds no inference. Restart reruns both collectors and diagnosis; selective reruns diagnosis using repaired source-backed configuration evidence, preserving independent telemetry. If this requires collection rather than deterministic repair, this 17-call design is invalid: revise and refreeze before launch.
Source-consistency prevention starts independently from the beginning, checks accessible source content/identity/version before consumption, and has its own three-call clean workflow. Apply the SAME frozen numeric-port transformation at the SAME pre-consumption stage before this arm's check, using its own freshly collected observations and the same deterministic eligibility rule; preserve exact exposure records. If its independent collection makes injection inapplicable, report that explicitly rather than treating a clean unexposed answer as prevention success. Charge checks and queries. It is not a post-fault recovery arm and its cost is compared end-to-end only.
All-expiry forks from the clean settled workflow; invalidate its initial artifact. Restart and selective must each rerun all three stages. Prevention is not applicable to expiry, since a fresh source can expire after it was checked. Application-request equivalence and retained-work counts are the key negative-control outcomes, not a required token speedup.

3. Deterministic fault eligibility (implementation gate pending)
Wrong content: consider only actually collected configuration GetAppYAML observations; canonical-sort by tool name, canonical arguments and observation ID. In the first eligible observation, alter the first line containing a numeric port, containerPort or targetPort value in 1..65534 by +1, preserving all other text. Save exact before/after spans and immutable pristine observation hash. Do not read answer labels or select a field because it changes the root answer. This differs from the development adservice-specific 9555 replacement and requires development validation before launch.
Eligibility is schema-based. If no eligible field is collected, record not-injected; no alternate fault/case is selected. Record applied, consumed, factually propagated, decision propagated, repaired and source-valid separately. Ignored/unpropagated faults remain in the full scheduled denominator. All-expiry is a version/contract intervention; a factually correct expired answer is not a factual error.
Any incoherence in the generic repair contract discovered on development requires v2 before held-out access. Do not label this new generic fault already validated by the old case-specific pilots.

4. Scoring and blindness
Freeze an input-only evidence checklist: root object/diagnosis, every decisive supporting factual claim anchored to observed text, no altered numeric fact presented as true, source IDs/versions current, no invalid descendants or obsolete publication, correction linked to prior output. Record supported/unsupported/uncertain per claim. Reviewer sees only agent-visible evidence and outputs, never benchmark diagnosis labels during this review; append native JRA/ECR after review is saved and hashed. Assistant review is not independent human adjudication. Student checks contested cases before final analysis, with corrections logged rather than erased.
Report native root score and native tool-path evidence completeness separately from factual support and workflow/source validity. Report TWO explicitly named joint gates: semantic joint = native root correctness AND sufficient observed factual support AND current valid publication; strict benchmark joint = semantic joint AND native ECR=1. Strict benchmark joint remains the primary quality gate used in the prior pilots; semantic joint is a separately declared diagnostic view, not a retrospective relaxation. Quality-preserving cost pairs use strict benchmark joint, with semantic-joint pairs shown only as a labeled secondary analysis. No-recovery can be semantically correct yet invalid. Report all scheduled units, including not-applicable, unconsumed, unpropagated, uncertain, provider error, timeout, rejected, cancelled and not-run; do not convert these into successful recovery.
Primary results: paired joint-success and recomputed/retained stages per incident, plus failure/exposure counts. Secondary: incremental and logical end-to-end token/call/tool/latency costs, paired savings restricted to jointly successful pairs with denominator displayed. Show both repetitions and within-incident range/mean; aggregate incident means equally. No significance or population p95 claim with three incidents.

5. Ordering and accounting
Canonical case order runtime, service, performance; repetition outer loop. Alternate restart/selective order using (case_index + repetition_index) parity. Clean prefixes are shared only as declared, never between repetitions. Store actual timings, prompt hashes, provider responses, usage and errors.
Physical budget charges shared requests once; logical method totals each include their relevant prefix. The clean diagnosis, unused by a wrong-content branch, is physical experimental overhead and not part of that branch's logical prefix. Prevention incurs its own complete prefix. Separate initial, recovery and total costs. Preserve failed work; no automatic retries. Do not combine old Codex subscription measurements with TritonAI dollar results as if same provider.
Reserve 17 calls per incident/repeat: clean3 + contaminated diagnosis1 + restart3 + selective1 + prevention3 + expiry restart3 + expiry selective3. Six units =102 calls, 6,120,000 token reservation. Separate development calibration ceiling18 calls/1,080,000 tokens. These are worst-case caps, not forecasts. Maximum input57,952 and output2,048 tokens per call; 180s timeout. Runner must enforce these limits before any paid call.
Dollar ceilings: formal $20, development $5, combined $25, and always <= verified remaining course API balance. Piazza32 conflicts between $50 and $25; conservatively cap at $25 until actual balance is checked. AWS credit is separate from API credit. Reserve whole formal batch using pinned input/output prices, including reasoning tokens in provider output accounting. At ceiling: 102*(57952*input_price_per_million + 2048*output_price_per_million)/1e6. If this exceeds $20 or available balance, do not start; revise scope/model in a versioned protocol before held-out access. No personal billing, no assumption of free API calls.
Unknown usage consumes full reservation. Stop if balance/model compatibility or safe full remaining reservation is uncertain. Keep partially completed matrix and not-run rows; do not rerun until an explicitly versioned new batch. Subscription task-token averages are not TritonAI cost estimates.

6. Launch gates and exit criterion
All manifest gates must pass, including generic fault and budget-enforcement tests on seen data, provider/model/pricing pin, course balance, benchmark acceptance evidence, and reproducible hashes. final_unlocked remains false. Exact model/prices cannot truthfully be frozen yet; freeze them in the launch annex before evaluation, not after outcomes.
Success of the research is a reproducible boundary characterization, not guaranteed savings. Negative, uncertain and non-propagating results are reportable. Dense graph scaling, wrong-root repair, new-application generalization, adversarial robustness, online memory learning and real queue-service guarantees are not claimed by this matrix.
