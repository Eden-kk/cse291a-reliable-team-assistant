1. 项目要回答什么
H1 恢复：在保证诊断与证据质量时，哪些依赖密度下选择性恢复比全重启省资源？验证/追踪开销何时抵消收益？
H2 来源：实际输入及共享知识版本追踪，相比citation-only能减少多少错误保留，代价是什么？
H3 调度：前台容量预留、公平/aging、恢复期限与完成优先如何影响首次有效响应、过期/错误结论更正、饥饿和吞吐？
H4 学习：从已解决开发事件生成、经过门槛验证的调查流程知识，是否改善后续独立事件的查询路径、证据闭环或总成本？与固定/不经门槛的更新相比如何？
统一链路：事件调查→候选流程知识→独立验证→版本发布→多个群消费→错误版本撤回→依赖失效→恢复任务与新告警共享预算。
保留负结果；完成研究不要求所有H都成立。

3. 数据、划分和冻结
主数据Cloud-OpsBench，commit ea05dafbc87b5985df8721622d63d4229c2b4224，MIT。服务事故使用原始快照与工具；只构造工作流故障、到达时序和模拟发布。
所有已使用/看过结果的15个案例列入development_seen。学习、门槛验证、集成调试与最终集分开；以configs/splits.json为唯一清单。
初始预留：learning6、gate-validation6、shakedown4、final8，按runtime/service/performance分层、固定seed抽样。预留不是承诺全部付费运行；预算不足时只在打开最终集前缩小，并记录理由。
当前只有case-ID级隔离；能够确认相同generator/template的近重复时，先成组再划分。未确认机制隔离就不得声称未见故障家族泛化。
只把question/允许工具观察传入模型；metadata.result、process-label、golden trajectory和答案目录名留在评分进程。模型无文件/网络工具。
最终集在configs/freeze.json记录代码commit、模型版本/alias、prompt、memory、门槛、fault/arrival manifest、token/调用预算hash后方可运行。脚本默认拒绝final_locked；明确解锁也必须有完整freeze。
最终失败只能用于下一研究版本，不能用其答案更新知识后重跑同一批并称新泛化。所有失败、超时、限额、格式错误和拒绝入队保留。
候选生成资料只来自learning/development_seen；选择候选和门槛只用validation。测试前固定知识版本。后续online学习若做，必须先评分再反馈，并单独报告反馈协议。

4. 工作流与角色接口
Configuration/status与Telemetry/dependency各自有上下文和工具选择；Coordinator读原始证据与两角色结果，可补充查询。
Memory必须在planner选择工具前显式提供；记录该步骤实际消费的版本，不能仅在最终答复追加建议。知识是条件→建议检查→证据/适用范围；不存具体测试事件答案。
运行ID分team/group/incident/step/attempt/epoch。每步存实际输入artifact版本、source版本、policy版本、查询、结果hash、模型/prompt/tool版本、usage、时间和状态。
原始观察不可被模型自信摘要替代；输出具对象/根因/引用约束。引用匹配不是语义真值；盲审抽样支持性。
工具只读；发布/工单写入先模拟并有动作账本。普通升级只影响新任务；撤回错误版本才失效实际消费者。缺失来源保守扩大重算。
恢复后拒绝旧attempt及已失效输入写入；无关epoch变化不应丢弃独立有效工作。保留已发布P1并追加P2关联更正；不得抹掉外部历史。恢复读干净的新状态，不能仅改版本号复用旧内容。
v0.1实现进程内恢复和追加式事件账本，在运行完成后导出日志；跨进程重启/实时持久化是后续里程碑，不能用日志存在宣称已具备。

5. 模型访问与费用门槛
E0先确认CSE291A账户/角色、模型权限、区域、API credit适用性和余额。CSE260账号及个人新付费API不用于本项目。
现在已有订阅可用于小型开发，但CLI包装token/缓存不能直接映射Bedrock价格。模型切换重新过开发校准门槛。
预算总上限$50：compute20、API15、storage5、reserve10，均为规划cap。先实测每类请求input/output/reasoning、失败重试、gate成本，再按当时允许provider价格计算上界。未验证之前不启动大矩阵。
每call保守预留输入估计+最大输出；返回后用actual usage结算，释放余量。未知usage按预留计费并停止新派发；actual超过cap记录overrun并停发。普通取消不能把已发请求当免费。
跟踪总calls/tokens、并发、每组额度、RPM/TPM及实际费用。v0.1先实现并发/总token预留；真实RPM/TPM限流、模型tokenizer与美元账本为E0/E1完成项。
每批最多10%可用实验预算；到API规划cap80%只允许分析/收尾，不再拓展；跨支出cap前重新明确资源方案。
大实验以tmux+caffeinate、日志、退出状态运行。AWS仅需要时开启，结束确认Stopped。当前阶段不需要GPU或常驻集群。

6. 分阶段实验矩阵（上限，不一次全部执行）
E0 Provider calibration
2–3个已见开发案例，串行及并发2，测API可用性/usage/延迟、失败与重试。并发不是研究结果。
通过条件：没有oracle访问；每call原始请求/回复/usage完整；预算账本可核对；明确失败状态；工具调用与输出合同有效。

E1 Clean workflow / query-stage memory plumbing
4个shakedown案例×固定/候选memory×1重复，最多8调查。在新代码上确保memory进入实际planner；保持模型、工具和总预算一致。
要求至少3/4根因及证据完整，并有逐例语义核验；否则仅用开发集修复，不打开final。
比较历史只作背景；不能把修复过的同一shakedown集作为最终测试。
工作流真实多Agent输出必须影响后续查询/判断；假后端只算软件集成测试。

E2 Learning
最终初始小批4案例×frozen/ungated/gated×1重复=12调查；预算允许扩至8×3×2=48。
至少生成3个自然候选，保存生成过程与被拒绝候选；constructed harmful controls单列。
候选生成成本、门槛验证、重试、拒绝候选均计入学习总成本；比较相同资料和候选集合，避免方法看见不同答案。
门槛预先固定：case级质量不得退化、无新语义/对象错误；成本门槛与权重在验证集确定，不在final调。安全失败时允许不更新。
gated/ungated同一候选时复用相同运行并明确等价，不能伪造策略差距。
指标：根因/对象、ECR、语义支持、查询次数/重复查询、达到证据所需calls/tokens、错误提升/拒绝、回归率与成本摊销。

E3 Recovery
初始4案例×2故障×3策略×1=24；上限8×2×3×2=96，另加可复用的clean/no-recovery对照。
故障：错误中间claim；错误/过期共享policy或观察版本。仅过期但值不变作为单独容易控制。
完整重启/选择性恢复共享已消费故障前缀、相同坏artifact身份和可查询环境；不提供根因答案。
Always-verify在进入下游前核对来源/版本/claim，其前缀可能不同，单独比较端到端结果。不能把通知后verify-all当作always-verify。
覆盖早/晚注入、独立分支、join、共享状态、密集污染、来源缺失、已发布后失效。实际被忽略的故障不算恢复成功。
自动故障检测不作为主要变量；误报/漏报若测独立报告。恶意指令与偶发错误单列。
指标：暴露/消费/传播率、错误保留、重算/保留有效工作、恢复正确性、source新鲜度、跨群/权限错误、过期写入、发布更正及总成本。

E4 Scheduling
先用E1–E3真实新trace做2/4群×间隔/突发/过载×FIFO/fair-aging/completion-aware×restart/selective=72个便宜回放条件；至少3固定arrival seeds，重复不当作独立事故。
分别报告known-cost replay和estimated-cost replay；后者加预先指定±25%用量估计误差。不得偷看未来真实耗时用于线上优先级。
正式live起步选2个arrival条件×2策略×1重复=4窗口，预算校准后最多2/4群×2负载×2策略×2重复=16窗口。用同一API容量、提示、arrival/fault schedule。
初次有效响应必须达到根因/证据门槛；报完成/未完成/拒绝数，不能只统计幸存者延迟。
同时报response SLO与recovery SLO，p50/p95、小样本范围、每群吞吐、最大ready wait、饥饿、抢占限制、预留浪费和未知usage。
过载必须比较限制活跃incident数和优先完成已有调查；减少拒绝可能增加响应排队，坦诚报告。
v0.1不能声称hard fairness或真实API成本上界；输出上界/供应商usage可验证后再升级。

E5 Integrated acceptance
三个固定窗口：部分知识污染、全污染、预算过载。按同一事件与到达seed比较完整设计及移除一个组件的变体；先1重复，预算允许2。
必须真正连接同一memory版本→实际模型上下文→产生的artifact→撤回→失效闭包→dispatcher恢复→新群响应→已发布历史修订。
模型/工具请求及输出成本均真实记录。受控fake/recorded backend的工程演示单列，不算语义或生产性能实验。
单个演示只能证明连接可运行；各组件因果贡献依靠E2/E3/E4。

7. 评分与统计
Primary joint success = correct object/root + native ECR + output contract valid + evidence support检查。四个分项同时报告；不能把ECR有值误当整体成功。
每个eligible case/window入分母；uncertain是未成功、无证据不能算正确、budget/timeout/provider failure另列原因，不删除。
延迟：arrival→首个达到明确质量标准的答复；revocation→正确linked correction。expiry-only替代计refresh latency，不称错误答案修复。
成本：initial/recovery/end-to-end，工具、LLM、candidate/gate、tracking CPU/storage、废弃/取消/重试都包含。物理共享prefix与每方法逻辑计费分开。
配对比较，按独立incident做cluster bootstrap；重复calls/groups不是独立样本。小样本仅报描述性结果/区间，不宣称普遍优势。
主图：质量-成本散点、恢复成本vs污染密度、first-response和correction双目标、预算压力-完成率、memory查询路径和回归案例。保存逐例CSV/JSON及生成脚本。

8. 实现验收
M0启动：独立repo/config/计划/历史proposal；无网络测试；memory真实进入请求；trace可读。
M1状态：不可变已验证policy，普通升级pin旧版本；错误撤回仅影响消费者；遗漏capture保守回退；跨team禁止访问；恢复重新绑定来源。
M2调度：输入估计+输出cap预留，actual结算；取消仍计费；未知usage/超限停发；不可负担foreground不占预留；无可运行任务明确交接。
M3端到端：A/B消费v1，C使用v2；撤回v1；A/B旧在途结果被拒，独立证据保留；恢复作业与C新任务同dispatcher执行；P1保留P2关联。
M4真实调试：在development/shakedown完成一次真实模型+只读工具的三角色调查与受控错误policy恢复；才解锁E2后续。
M5完整Phase1：native checker、clean/传播与full restart/alwaysverify，文档和复现。
M6正式study：选择性恢复、学习/调度消融、E5及失败分析。

10. 范围与停止条件
所有三组件都是核心。暂不加入完整Slack/企业IM、真实运维写权限、多模型路由、训练权重、Kubernetes集群或复杂UI。
模型能力不达E1门槛：只用dev修复/更换已允许模型，freeze前重新校准。
预算未知/耗尽：停新派发并保留inflight账本，缩小样本而不删负例；不自动购买或用reset额度。
主实验结果不理想：保留失败与机制解释，不能换case或训练到test成功。研究结论可为“该条件不值得复用/学习/优先前台”。
工作任务与状态以docs/status.txt为准；未完成项不得写入简历为既成结果。
